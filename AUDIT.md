# Аудит MRX Desktop

Дата: 21.10.2026 · Коммит: `299776a` · Объём: `app/server.mjs`, `app/separate-worker.mjs`, `app/public/*`, `desktop/*.cjs`, `scripts/build-portable.ps1`, `tests/*`, собранные `dist/MRX` и `dist/MRX.zip`.

Ссылки на строки в разделе «Находки» указывают на код коммита `299776a`, до исправлений.

Метки: **[воспроизведено]** означает, что проблема подтверждена запуском; **[по коду]** означает, что вывод сделан по чтению кода и не запускался.

## Итог

Проект аккуратный: локальный сервер хорошо защищён от браузерных атак, окно Electron изолировано, интерфейс не подвержен XSS, все 11 бэкенд‑тестов проходят. Основные риски связаны не с безопасностью, а с надёжностью:

1. Сервер падает, если хотя бы один файл не удаётся прочитать при отдаче.
2. Загрузка зависает, если не удаётся записать временный файл.
3. При сбое сервера на старте приложение закрывается без сообщения.

Также место на диске растёт без ограничений, а из чистого клона сборка не воспроизводится.

## Что проверено и в порядке

- **Тесты:** 11 из 11 проходят на Node 25.2.1 и на встроенном в сборку Node 22.14.0 (`backend.test`, `backend-export.test`, `backend-regressions`).
- **`npm audit --omit=dev`:** 0 уязвимостей. Все пакеты в `package-lock.json` берутся из registry с `integrity`. Локальных патчей нет: `package/` совпадает с `node_modules/@audio/neural-separate`.
- **Сборка соответствует исходникам:** `dist/MRX/resources/app` и `dist/MRX.zip` совпадают с текущим кодом, разница только в финальном переводе строки.
- **В `MRX.zip` нет пользовательских данных:** внутри только `.gitkeep`. При этом в папке `dist/MRX` уже лежит `data/electron-user-data` от локальных запусков, поэтому ZIP нужно собирать только из свежей папки.
- **Безопасность:**
  - Сервер слушает только `127.0.0.1`.
  - Строгая проверка `Host` защищает от DNS rebinding.
  - Каждый POST проверяет cookie `HttpOnly; SameSite=Strict`, а также `Origin` и `Sec-Fetch-Site`.
  - Окно Electron: `sandbox`, `contextIsolation`, `nodeIntegration: false`, запрет `window.open` и навигации на чужие адреса.
  - Весь интерфейс строится через `textContent`, поэтому XSS нет.
  - Скачивание и экспорт проверяют пути, включая `realpath`.
  - FFmpeg запускается с `-protocol_whitelist file,pipe`.
  - SHA‑256 проверяется для Node, Electron и модели.

## Находки

### Высокий приоритет

#### 1. Ошибка чтения файла при отдаче роняет весь сервер — [воспроизведено]
[server.mjs:548-559](app/server.mjs:548). `serveFile` вызывает `createReadStream(filePath).pipe(res)`, но не обрабатывает `'error'` у потока чтения. Если `stat()` прошёл, а открыть файл не получилось, Node выбрасывает необработанную ошибку, и процесс завершается.

- **Проверка:** копия `app/` запущена на встроенном Node 22.14.0, у отдаваемого файла запрещено чтение данных (`icacls /deny user:(RD)`). Запрос завершился `ECONNRESET`, сервер упал с `exit code=1` и сообщением `Unhandled 'error' event`.
- **Где срабатывает:** эта функция отдаёт статические файлы, WAV, ZIP задачи и общий архив «Сохранить всё».
- **Реальные причины:** антивирус держит файл открытым (EBUSY/EPERM), файл удалили между `stat` и `open`, проблемы с правами.
- **Последствия:** Electron показывает «Локальный сервер неожиданно завершился», очередь и текущая обработка теряются.
- **Вторая проблема там же (по коду, не запускалось):** если скачивание прервано, `pipe` только отсоединяет поток чтения, но не закрывает его. Дескриптор остаётся открытым, и на Windows это может мешать удалению папки результата.
- **Исправление:** `stream.pipeline(createReadStream(...), res, cb)`. В `preview()` ошибки потока уже обрабатываются вручную ([server.mjs:646-662](app/server.mjs:646)), а `serveFile` эту обработку не получил.

#### 2. Загрузка зависает, если не удалось записать временный файл — [воспроизведено]
[server.mjs:203-216](app/server.mjs:203). Механизм:

1. При ошибке записи `out` (например, ENOSPC) `pipe` отсоединяет источник.
2. Поток файла busboy никто больше не читает.
3. Busboy не доходит до `finish`.
4. `saveMultipart` не завершается ни успехом, ни ошибкой.

- **Проверка:** на встроенном Node 22.14.0 вместо `data/uploads` подложен файл, отправлено 8 МБ. Ответа нет ровно 300 секунд, после чего Node обрывает запрос с пустым `HTTP 408` (это срабатывает `requestTimeout` по умолчанию).
- **Последствия:** 5 минут интерфейс показывает «Загрузка», новые файлы добавить нельзя, кнопка «Закрыть» неактивна. Затем появляется непонятное «Не удалось добавить файлы (код 408)», а настоящая причина (например, нет места на диске) не сообщается.
- **Реальная причина:** закончилось место на диске при загрузке больших видео (лимит 1,5 ГБ × 20 файлов). Учитывая находку 4, это вполне вероятно.
- **Исправление:** в `out.on('error')` вызывать `stream.resume()` и `failUpload(...)`.

#### 3. При сбое сервера на старте приложение закрывается молча — [воспроизведено]
[main.cjs:104-112](desktop/main.cjs:104). Пока окно не создано, `mainWindow === null`. Поэтому обработчик `exit` выбирает ветку «ожидаемое завершение» и вызывает `app.quit()` раньше, чем успевает сработать `showStartupError`.

- **Проверка:** запущен `dist/MRX/MRX.exe`, сервер завершился с кодом 1 при `listen`. MRX.exe закрылся с кодом 0 меньше чем за секунду, без окна и без диалога. В журнале есть `Server exited code=1`, но нет `Startup failure`.
- **Реальные причины:** заняты все 20 портов, повреждённая или неполная распаковка (нет модуля), антивирус поместил `runtime\node.exe` в карантин.
- **Исправление:** если сервер завершился до `startupReady`, считать это ошибкой запуска и показывать диалог со ссылкой на журнал.

### Средний приоритет

#### 4. Место на диске растёт без ограничений — [по коду]
В коде нет ни одной процедуры очистки:
- **`data/outputs/<id>/`:** для каждой задачи сохраняются 3 WAV и ZIP задачи. ZIP создаётся сразу ([server.mjs:309](app/server.mjs:309)), даже если его не скачают, и почти удваивает объём, потому что PCM почти не сжимается. В интерфейсе нет способа удалить результаты. После перезапуска задачи не видны, но папки остаются.
- **`data/cache/exports/*.zip`:** каждое «Сохранить всё» с новым набором файлов создаёт ещё одну полную копию. Список архивов хранится только в памяти, а сами файлы переживают перезапуск.
- **`data/uploads/`:** если процесс убит или упал, входные файлы остаются. Удаление происходит только в `finally` ([server.mjs:328](app/server.mjs:328)).
- **Завершение работы:** `rm(outputDir)` вызывается, пока worker ещё пишет файлы ([server.mjs:766-770](app/server.mjs:766)). На Windows это может дать EBUSY и оставить частичные результаты.

Каждая обработка занимает место 2–4 раза: WAV, ZIP задачи, общий ZIP и копия через диалог сохранения.

**Исправление:** при старте очищать `uploads/` и `cache/exports/`, собирать ZIP задачи при скачивании потоком, добавить кнопку «Очистить результаты» или срок хранения.

#### 5. Каждый файл копируется через HTTP, общий лимит 5 минут — [по коду]
В desktop‑версии файл уже лежит на диске, но [app.js:843](app/public/app.js:843) отправляет его на сервер целиком, а сервер пишет копию в `uploads/`. Это удваивает расход диска и время. Кроме того, по умолчанию в Node `server.requestTimeout = 300 000 мс` на **весь** запрос, то есть на все файлы сразу. Если загружать много больших видео на медленный диск, загрузка оборвётся.

**Исправление:** в Electron передавать пути через preload (`webUtils.getPathForFile`). Как минимум, явно задать `requestTimeout` для `/api/jobs`.

#### 6. Устаревшие и незакреплённые компоненты — [по коду]
- **Node 22.14.0** (февраль 2025): именно эта версия парсит HTTP с недоверенными загрузками. Стоит обновить до актуального 22.x или 24.x LTS и закрепить новый SHA‑256.
- **FFmpeg** взят из ночной сборки BtbN `master-latest`, а не из релиза, хотя декодирует недоверенные файлы пользователя. Скрипт только записывает хэш FFmpeg, но не сверяет его с ожидаемым ([build-portable.ps1:148](scripts/build-portable.ps1:148)). Лучше использовать релизную ветку и проверять хэш так же, как для Node и Electron.

#### 7. Сборка не воспроизводится из чистого клона — [по коду]
- `weights/` и `tools/ffmpeg-staging/` исключены в `.gitignore`. Скрипт их не скачивает, а только проверяет хэш модели ([build-portable.ps1:53](scripts/build-portable.ps1:53)). README упоминает Hugging Face, но шага загрузки модели нет.
- Скрипт копирует локальную `node_modules` целиком ([build-portable.ps1:103](scripts/build-portable.ps1:103)) вместо чистого `npm ci --omit=dev`, поэтому в сборку попадает всё, что лежит локально. Туда входят зависимости установщика `onnxruntime-node`: `adm-zip`, `global-agent`, `tar-stream` и другие.
- В `runtime/` попадает полный npm и corepack (2942 файла в ZIP), хотя приложению нужен только `node.exe`.
- Поиск VC++ рекурсивно обходит весь `Program Files` ([build-portable.ps1:57-64](scripts/build-portable.ps1:57)), поэтому шаг медленный, а результат зависит от того, что установлено на машине.

#### 8. Windows показывает приложение как «Electron» от неизвестного издателя — [воспроизведено]
`MRX.exe` не подписан (`NotSigned`). В его метаданных указано: `Product: Electron`, `Company: GitHub, Inc.`, `Version: 44.9.0`, иконка тоже от Electron. SmartScreen покажет предупреждение «Неизвестный издатель», а в диспетчере задач процесс будет называться «Electron».

**Исправление:** прописать метаданные и иконку через rcedit, подписать exe, выключить ненужные fuses Electron (`RunAsNode`, `EnableNodeCliInspectArguments`).

#### 9. Токен сессии выдаётся любому локальному клиенту — [по коду]
- `GET /api/state` ставит cookie сессии на любой запрос, который прошёл проверку `Host` ([server.mjs:668-670](app/server.mjs:668)).
- `download` и `preview` вообще не проверяют сессию ([server.mjs:561](app/server.mjs:561), [server.mjs:601](app/server.mjs:601)), хотя `downloadExport` проверяет.

От браузеров эта схема защищает. От другого процесса или **другого пользователя Windows** на той же машине (RDP, терминальный сервер) не защищает: loopback у сеансов общий. Такой пользователь может увидеть очередь, скачать дорожки и закрыть приложение. На личном ПК риск низкий.

**Исправление:** Electron генерирует токен, передаёт его серверу через env и ставит cookie через `session.cookies.set` до `loadURL`. Без cookie сервер отвечает 403.

### Низкий приоритет

10. **Ложный баннер «MRX недоступен» при отключении Wi‑Fi** — [app.js:1029](app/public/app.js:1029). Событие браузера `offline` переводит офлайн‑приложение в состояние «нет связи» примерно на 3 секунды. Обработчик стоит удалить.
11. **Лимит 1,5 ГБ PCM (около 71 минуты стерео) обнаруживается только после декодирования до этого предела** — [separate-worker.mjs:67-75](app/separate-worker.mjs:67). Пользователь ждёт, а потом получает ошибку. Пиковая память до запуска модели примерно в 4 раза больше PCM (около 6 ГБ на пределе), потому что данные лежат одновременно в кусках, в `Buffer.concat`, во `Float32Array` и в L/R. Можно раскладывать каналы прямо из кусков. Если поднять лимит, WAV больше 4 ГБ упадёт на `writeUInt32LE`.
12. **Усиление Electron** — [main.cjs](desktop/main.cjs):
    - нет CSP в [index.html](app/public/index.html);
    - нет `setPermissionRequestHandler`, а по умолчанию Electron разрешает запросы;
    - `ipcMain.handle` не проверяет отправителя;
    - `NODE_OPTIONS` пользователя передаётся встроенному Node ([main.cjs:71](desktop/main.cjs:71)), и с чужими опциями приложение может не запуститься;
    - если `runtime\node.exe` отсутствует, используется `node` из PATH ([main.cjs:70](desktop/main.cjs:70)), хотя в сборке нужна ошибка;
    - тестовые хуки (`--mrx-smoke`, `MRX_SMOKE*`) включены в рабочую сборку.
13. **Мёртвый код** — `parseBody` ([server.mjs:121](app/server.mjs:121)) нигде не используется.

- Тест экспорта использует `adm-zip`, который не объявлен в зависимостях и приходит транзитивно от `onnxruntime-node`.
- Нет CI. Native‑ и e2e‑проверки требуют собранной portable‑папки.

### Лицензии (решение за владельцем)

- В карточке модели, которую формирует сам скрипт сборки ([build-portable.ps1:203-205](scripts/build-portable.ps1:203)), сказано, что модель обучена на Divide and Remaster v2, а у исходных наборов данных есть некоммерческие условия. В README модель указана просто как MIT. Если планируется коммерческое распространение, это стоит проверить с юристом. Это риск, а не вывод.
- По LGPL FFmpeg всё оформлено правильно: в комплект входят точный архив исходников, provenance, текст лицензии, а FFmpeg запускается отдельным процессом.
